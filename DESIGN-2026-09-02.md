## 1. Vision

WebRMS-Next **owns its data**: every install keeps its own SQLite database and runs fully standalone (no SQL Server, no live system, no network). It can additionally **pull from existing AKPOS-based live systems** through a connector layer — to run *alongside* them, or to make *migrating off them* a scripted, verifiable process. Reads never hit the live system at request time — they hit the local DB; live systems are data sources, not dependencies.

```
                     ┌────────────────────────────────────────────┐
                     │            AKPOS live systems              │
                     │  new-gen HoS (100.71.113.111)              │
                     │  old-gen HoS (graduatehos-old)             │
                     │  BoS boxes (BethSC, WelcB, 342, …)         │
                     └──────┬──────────────────────┬──────────────┘

                     ┌──────▼──────────────────────▼─────────────┐
```

## 3. Own database (SQLite)

Per-install `data.db`; every business table carries **provenance columns** so data from any source merges safely:
`source TEXT` (`local-connector` | `hos-snapshot` | `seed`), `source_key TEXT` (AKPOS pk), `last_synced_at`, `is_active`.

**ID strategy (O-1):** replicated tables (orders, paid, config, rebates, item-change requests, audit) use **UUID PKs or `(origin_install, local_id)`** — SQLite AUTOINCREMENT collides across installs. Connector-materialized tables keep integer ids keyed by `source_key`.

**Timezone (O-8):** store UTC + per-branch offset; render local. Decided at P0, not retrofitted.

**Key tables (full DDL in P0):**

| New table | Mirrors | Notes |
|---|---|---|
| `branches` | Branches | `ext_key`, `is_ho`; **branch-mapping config** maps old-system ids → new ids (new HoS 10–17 vs old HoS 336–342) |
| `departments` | Departments | ext_key, target_margin |
| `suppliers` | Customers (CustType='R') | ext_key = code (010, 013, …) |
| `items` | Items + ItemBarcodes | upc, dept, supplier, parent_upc, pack_qty, costs, selling_qty, inactive; `barcodes` child table |
| `sales_daily` | ItemMovement (aggregated) | `UNIQUE(branch,item,date)`, units + revenue + promo split — aggregate at ingest, never raw rows |
| `stock_current` | ItemMovement (latest per branch) | **on-hand per branch/item, refreshed every poll (G-1)** — feeds order sheet, sellout, stock reports; handles transfers 'T' between branches |
| `receipts` / `receipt_lines` | SMHeaders P/G/I/**Z** + SMDetails | 3-part key transno+branch+station; **'Z' returns included** so net bills-due = goods-in − returns (G-2) |
| `item_cost_history` / `item_price_history` | Items.Cost / Price1 at ingest | cost + price history for GP% audits, cost-trend, promo effectiveness (C2/G-8) |

| `orders` / `order_lines` | (orders.json today) | same fields as the JSON log |
| `incoming_pos` | (files + bol sidecar) | filename, bol, status |
| `settings`, `supplier_modes`, `supplier_terms`, `paid_ledger` | (JSON/TOML today) | config becomes DB rows |
| `rebate_contracts` / `rebate_contract_lines` / `rebate_ledger` | app-authored | **scanback + supplier rebate tracking (app-only)** — contracts/expectations/receipts all app-owned, works in every mode; **recorded from the Active Specials view** (per-special, `special_id`-linked), supplier/dept rebates without a special via contract lines; HoS-authored, outbox-replicated. See LIVE-DB-FINDINGS-2026-09-02.md |
| `audit_log` | EventLog (live) | operator audit trail (B_Users operator), same txn as outbox writes |

**File sidecars that survive:** ETL `.xlsx` outputs (PO, stocktake, AP exports) stay on disk — deliverables, not state. `save-mode.json` stays per-install.

## 4. Connector layer (pull from live systems — PRIMARY path)

A `Connector` trait, one implementation per live-system type, all tiberius-backed:

```rust
trait Connector: Send + Sync {
    fn probe(&self) -> ServerInfo;                            // mode, branch, db_ok (today's detection.rs)
    fn pull_branches(&self) -> Vec<Branch>;                   // + depts, suppliers
    fn pull_items(&self, hw: &HighWater) -> PullResult<ItemBatch>;
    fn pull_sales(&self, hw: &HighWater) -> PullResult<SalesBatch>;     // ItemMovement → sales_daily
    fn pull_receipts(&self, hw: &HighWater) -> PullResult<ReceiptBatch>; // SMHeaders P/G/I + details
    fn pull_ap(&self, hw: &HighWater) -> PullResult<Vec<ApInvoice>>;
    fn pull_promos(&self) -> Vec<PromoRule>;                  // Specials OR RBP pricing tables
}
```

- **Source implementations:** `NewGenHosConnector` (100.71.113.111, RBP), `OldGenHosConnector` (Specials), `BosConnector` (per-box). The existing module queries (stocktake 562 LOC, ordering 746, promotions 1545, reports 2546) port nearly verbatim behind the trait.
- **Every install has its own connector** to its *own* AKPOS (BoS box → its local AKPOS; HoS → the group DB). This is the **primary** data path.
- **Incremental:** high-water marks per source+table (ItemMovement IDs, SMHeaders Logged, Items.LastUpdate). Poll on the existing ≤15 min + "Sync now" cadence.
- **Branch mapping:** config table `source_branch → new branch id`; multi-source conflicts resolved by `last_synced_at` (newer wins).
- **RBP (new-gen pricing) ports wholesale:** `rbp.rs` becomes a pure fn over `promo_rules` (RETAIL/LOCAL/PROSET forms unchanged).

## 5. Replication (between WebRMS-Next installs)

Same roles/cadence/transport as today (REST over Tailscale, poll 15 min + manual). Two down-channels:

### 5a. Transactional outbox (orders, config, paid, POs) — as before
Every local write to a replicated table appends to `outbox(id, table, row_id, op, payload, origin_install, ts)`; clients push up, HoS merges, fans down, clients apply idempotently. Ownership rules preserved:
- `orders` → bidirectional per destination branch
- `settings`, `supplier_modes`, `supplier_terms`, `paid_ledger` → HoS-class authored, Remote-HoS pushes up, propagated down (b285e95 model)
- `incoming_pos` → up from clients, read-only elsewhere

### 5b. Catalog snapshot down (FALLBACK path for BoS installs) — NEW
When a BoS install's **own connector cannot reach its AKPOS**, it falls back to a **read-only catalog snapshot replicated from the HoS** — the HoS already materializes the group-wide data (items, suppliers, departments, branches, `promo_rules`, `sales_daily` for all branches, receipts, AP) via its own connector, so it can serve it.

- **Channel:** `GET /api/sync/down/snapshot?table=&since=` — chunked, per-table, high-water marked (NOT the outbox; bulk catalog data would bloat it).
- **Application rule:** snapshot rows land in the same tables tagged `source='hos-snapshot'`, and **never overwrite a newer local row** (LWW on `last_synced_at`) — so when the local connector comes back, its fresh pull supersedes the snapshot automatically. Reads just read the local DB; staleness is visible in the UI (badge shows `data via HoS snapshot, HH:MM ago`).
- **Why it's seamless:** the app only ever reads the local DB. Primary and fallback are both just materializers; whichever is healthy refreshes the rows.
- **HoS side:** no new work — its connector output IS the snapshot source; a read-only HTTP view over its own DB.
- **Standalone installs** (connector off, no HoS): no snapshot; fully local by definition.

**Not replicated** (each install materializes via its connector, or via 5b): `items`, `sales_daily`, `promo_rules`, `receipts`, `ap_invoices` as *primary* data — they flow through 5b only as the BoS fallback.

## 6. Independence & migration paths

Three operating modes, one binary, mode from config:

| Mode | Connector | Writes | Result |
|---|---|---|---|
| **Standalone** | off | own DB | fully independent; nothing else on the network |
| **Alongside** | on (incremental) | own DB; POs exported as ETL `.xlsx` for the old system (reuse `build_purchase_order_xlsx`) | live systems keep working; run in parallel |
| **Migrated** | off after seed+parity | own DB | old system read-only or decommissioned |

**Migration runbook (P4 tooling):**
1. `seed --source <connector> --depth 36mo` — full pull: items, suppliers, depts, branches, **36 months** sales, receipts, AP, promos. Idempotent (upserts on source_key).
2. Run alongside — incremental pulls keep it fresh; operate both for a real cycle.
3. `parity-report` — go/no-go gate: row counts, AP owed, receipts value, GP%, sellout sanity (the validation methods already in the review docs). **No cutover without a reviewed parity report.**
4. Cut over — connector off, old system read-only; BoS boxes replicate from the new HoS, no AKPOS access needed anywhere.

## 9. Risks

- **ItemMovement volume** — mitigated: aggregate to `sales_daily` at ingest; 36-mo depth is the ceiling (≈2–6 GB estimated, composite PK `(branch,item,date)` + covering indexes; monthly rollup optional later).
- **Snapshot staleness (5b)** — mitigated: LWW per row, never overwrites newer local data, UI badge shows age; operators know data may lag while the direct path is down.
- **Two HoS generations, different pricing schemas** — mitigated: `promo_rules` kind+payload + ported RBP resolver; connector per generation.
- **Parity trust** — mitigated: `parity-report` gate before cutover; live-verification rule.
- **SQLite single-writer** — fine per install (single process); replication serializes through outbox.
- **Scope is the real risk** — P2 is the long pole; mostly mechanical porting of proven code; each phase stands alone.
